# 全登壇の自動解析と蓄積

## 処理の流れ

1. yt-dlpから動画の長さ・チャプターを、curlから公式スケジュールを自動取得します。利用者が秒数を入力する必要はありません。
2. 最大30分ずつの映像・音声をGeminiへ渡し、話者・タイトル・登壇境界・識別根拠を構造化JSONとして取得します。スケジュールは名称の参考に使い、予定時刻をアーカイブの時刻に置き換えません。
3. 指定範囲に隙間・重複・範囲外がないかを検査します。判別できない部分はunknownとし、除外せず保存・解析します。Welcome・待機・休憩等はotherとして詳細解析から除きます。
4. 隣接区間で同じ講演キー・氏名・種類と識別されたものを結合します。長い講演は再び最大30分ずつに分けて詳細解析します。識別名が揺れた場合は別資料に分かれる可能性があり、完全な話者同定を保証しません。
5. 詳細解析プロンプトの原文全文に対象区間と識別結果を付加し、Markdownを取得します。画面にしか出ないコード・図表・デモも対象です。映像と識別結果が異なる場合は、その不一致を記すよう求めます。
6. 元動画の時刻・URL・使用量・生成条件とともに `notes/<イベント>/talks/` へ保存します。
7. 指定された登壇区間の解析がすべて揃ったものを、省略せず `notebooklm/<イベント>/` の独立したMarkdownへ結合します。索引・処理状態も自動更新します。

## テストと本番の共通化

`test`と`all`は同じ処理を使用します。testは冒頭の最大30分を識別し、Evan Youの区間だけを詳細解析します。allは取得した動画の長さまで処理し、全登壇と未識別区間を詳細解析します。テストの部分資料を本番の長い講演と二重に連結しないよう、今回の区間分割に一致する本文だけを使用します。

設定は `config/viteconf-2026.json` です。以前の「最初の1800秒より後を拒否する」制約は削除しました。各API入力の長さを最大1800秒にする制約は、全編を1入力に送らず処理するために残しています。

## 生成方式と再開

GenerateContent APIの同期REST、`gemini-3.8-flash`、YouTube直接入力、`fileData` + `videoMetadata`、既定のStatic方式を維持します。登壇識別には公式資料で確認した `generationConfig.responseFormat.text` のJSON schemaを使用します。APIへのモデル・方式の自動切り替えはありません。

モデルと送信JSONのハッシュをキャッシュのキーにし、正常な応答を再利用します。HTTP 200、curl終了0、APIエラーなし、候補1件、終了理由STOP、空白以外の本文があることを確認します。思考本文・署名を除いて抽出し、欠落した使用量はnullとします。生レスポンスとログは.local内だけに保存します。

登壇識別のJSONが不正な場合はキャッシュを無効扱いとし、次回に再処理します。詳細解析が失敗した講演は未完了とし、他の解析は継続します。ただし認証・権限・割当エラーでは以降の送信を停止します。無制限の再送や自動の全編再解析はしません。

## 自動保存と正確性

人による確認は保存・次の講演への進行の必須条件にしません。全生成資料にAIによる推定・人による未照合であることを示し、本文の「確認済み」を人が確認した事実と扱いません。発言、映像、補足、不明点を区別するよう求めます。

通常のStatic処理は1秒1フレームとの公式説明があり、速い操作や小さいコードの全情報取得を保証しません。登壇境界・話者・API名・数値・引用の正確さは、自動化しただけでは保証できません。機械的な正常応答と学習内容の正確性を区別します。`status.json`の完了は指定区間の処理が揃ったことを表し、内容の第三者検証や講演全体の収録完了を意味しません。

NotebookLM用Markdownの生成までを自動化し、NotebookLM自体の操作・新しいWebアプリ・サーバーは追加しません。
